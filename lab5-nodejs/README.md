# Лабораторная работа № 5 — Node.js: файловая система, CLI, потоки и Worker Threads

## Предметная область

Каталог товаров — продолжение темы каталога товаров из предыдущей лабораторной работы. Приложение работает целиком через командную строку, хранит каждую запись в отдельном JSON-файле и ведёт индекс для быстрого вывода списка.

## Структура проекта

```text
lab5-nodejs/
├── app.js                         # точка входа и разбор CLI-команд через process.argv
├── package.json                   # тип модулей и npm-команды; внешних зависимостей нет
├── data/
│   ├── index.json                  # индекс записей каталога
│   ├── records/                    # отдельный <id>.json для каждого товара (создаётся автоматически)
│   ├── large-products.jsonl        # большой тестовый набор (генерируется командой)
│   ├── stream-output.txt            # результат Writable Stream
│   └── transformed-products.jsonl   # результат Transform Stream
├── experiments/
│   └── event-loop.js               # эксперимент с синхронным кодом, Promise и setTimeout
└── src/
    ├── fs/
    │   └── records.js              # CRUD, индекс, поиск, переименование и резервная копия
    ├── streams/
    │   └── stream-ops.js            # генерация большого файла, Readable/Writable/Transform, benchmark
    └── workers/
        └── compute-worker.js        # вычисление в отдельном Worker Thread
```

## Требования

- Node.js 20 или новее (используются современные API `fs.cp` и `node:`-импорты).
- Установите Node.js с официального сайта: https://nodejs.org/
- Внешние npm-пакеты не требуются.

## Запуск

Откройте терминал в каталоге проекта:

```bash
cd lab5-nodejs
node --version
node app.js help
```

Для запуска не требуется `npm install`, но команды npm также доступны:

```bash
npm start -- help
npm run event-loop
npm run generate-large
npm run benchmark
npm run compute-main
npm run compute-worker
```

## Команды CLI

Все команды запускаются из папки `lab5-nodejs`.

| Команда | Назначение |

| `node app.js create "Мышь" "Периферия" "2499.90" "12"` | Создать товар. В ответе выводится созданная запись и её ID. |
| `node app.js read <id>` | Прочитать товар по ID. |
| `node app.js list` | Вывести индекс всех товаров. |

| `node app.js delete <id>` | Удалить JSON-файл товара и запись из индекса. |
| `node app.js rename <id> <новый-id>` | Переименовать файл и обновить ID в индексе. |
| `node app.js search` | Интерактивно искать по названию или категории через `readline`/stdin. Поиск регистронезависимый. |
| `node app.js backup [источник] [назначение]` | Рекурсивно скопировать каталог. По умолчанию копируется `data` в `backup`. |
| `node app.js generate-large [количество]` | Сгенерировать большой JSON Lines файл (по умолчанию 150 000 строк). |
| `node app.js stream-read [файл]` | Прочитать файл через Readable Stream и посчитать байты/чанки. |
| `node app.js stream-write [текст]` | Записать данные через Writable Stream. |
| `node app.js transform [файл]` | Потоком преобразовать категории в верхний регистр, сохранив JSONL-формат. |
| `node app.js benchmark [файл]` | Сравнить `fs.readFile` и потоковое чтение одного файла. |
| `node app.js compute main [итерации]` | Выполнить вычисление в основном потоке. |
| `node app.js compute worker [итерации]` | Выполнить то же вычисление в Worker Thread. |
| `node app.js help` | Показать справку. |

ID генерируется из времени и случайного суффикса, а перед созданием дополнительно проверяются индекс и целевой путь. ID файлов допускают латинские буквы, цифры, дефис и подчёркивание.

## Схема движения данных

```text
CLI (process.argv / readline stdin)
            |
            v
          app.js
            |
      +-----+------------------------+
      |                              |
      v                              v
src/fs/records.js             src/streams/stream-ops.js
      |                              |
      v                              +--> Readable --> Writable
data/index.json                       +--> Readable --> Transform --> Writable
data/records/<id>.json               +--> fs.readFile vs Readable benchmark
                                     |
                                     +--> Worker Thread --> результат
```

## Где и как используется файловая система

- `src/fs/records.js` реализует создание, чтение, изменение, удаление и список записей, а также переименование, интерактивный поиск и резервное копирование.
- Каждая запись лежит отдельно в `data/records/<id>.json`. Это позволяет читать или менять одну запись без загрузки всего каталога.
- `data/index.json` хранит краткие поля записей для команды `list`. При CRUD-операциях индекс синхронизируется.
- Запись индекса сначала выполняется во временный файл `index.json.tmp`, затем временный файл переименовывается в `index.json`. Это снижает риск оставить индекс частично записанным.
- `fs.cp` рекурсивно копирует каталог для backup. Нельзя выбирать каталог назначения внутри исходного: это могло бы вызвать рекурсивное копирование.
- Ошибки чтения, отсутствующие файлы/записи, некорректный JSON, недопустимые значения, конфликт ID и недостаток аргументов обрабатываются понятными сообщениями с кодом завершения 1.

### Почему отдельный файл для каждой записи и индекс

Отдельные JSON-файлы упрощают адресное чтение, обновление и удаление. Индекс — компактный список для команды `list`; иначе пришлось бы открывать и разбирать каждый файл при каждом показе списка. ID не зависит от названия товара, поэтому переименование названия не требует переименовывать файл.

## CLI: process.argv и stdin

`process.argv` — массив аргументов процесса. Обычно элемент 0 — путь к исполняемому файлу Node.js, элемент 1 — путь к скрипту, а с элемента 2 идут аргументы, переданные пользователем. Например, в команде `node app.js read p_123` аргументы приложения — `read` и `p_123`. Аргументы приходят строками, потому что командная строка передаёт текстовые значения; числа нужно явно преобразовать и проверить.

Аргументы командной строки подходят для параметров, известных при запуске. `stdin` — поток входных данных, из которого можно читать ввод пользователя уже после старта. Команда `search` использует `readline`, чтобы запросить поисковую строку интерактивно.

Если аргументов недостаточно, программа показывает синтаксис команды, пишет понятную ошибку и завершает команду с `process.exitCode = 1`, а не обращается к отсутствующим значениям.

## Эксперимент Event Loop

Файл: `experiments/event-loop.js`.

До запуска прогноз: `A, D, C, B`.

Запуск:

```bash
node experiments/event-loop.js
```

Ожидаемый вывод:

```text
A
D
C
B
```

Объяснение: `console.log('A')` и `console.log('D')` — синхронный код, выполняются сразу в порядке записи. Callback `Promise.then` попадает в очередь микрозадач и выполняется после текущего синхронного участка. Callback `setTimeout` выполняется позже, когда Event Loop дойдёт до соответствующей фазы таймеров. Задержка 0 мс не означает «выполнить немедленно».

**Требование отчёта:** перед запуском запишите свой прогноз, затем запустите скрипт и укажите фактический вывод. Для данного примера ожидаемый порядок — `A, D, C, B`.

## Streams

### Большой файл

Команда `node app.js generate-large 150000` создаёт JSON Lines файл `data/large-products.jsonl`: одна JSON-запись на строку. Это тестовый набор, а не основной индекс каталога. Размер можно менять аргументом (от 1 до 2 000 000 строк).

### Readable, Writable и Transform

- **Readable Stream** — источник данных. `fs.createReadStream` читает файл порциями, а не возвращает сразу весь файл как один большой буфер.
- **Chunk** — очередная порция байтов/данных, переданная потоком.
- **Writable Stream** — приёмник данных. `fs.createWriteStream` записывает текст в файл. При `write()`, вернувшем `false`, код ждёт событие `drain`, учитывая backpressure.
- **Transform Stream** — одновременно читающий и записывающий поток, который преобразует данные. В этой работе он разбирает строки JSONL и переводит категорию в верхний регистр.
- **`pipe()`** соединяет источник и приёмник, передавая данные дальше и помогая управлять потоком. В проекте применяется `pipeline()` из `node:stream/promises`: он удобен тем, что возвращает Promise и корректно сообщает об ошибках цепочки.

Потоковый трансформер учитывает, что граница чанка не обязана совпадать с концом строки: незавершённый хвост хранится до следующего чанка. Это важно, иначе одна JSON-запись могла бы случайно разделиться между двумя порциями.

### Эксперимент сравнения чтения и памяти

1. Создайте файл: `node app.js generate-large 150000`.
2. Выполните `node app.js benchmark`.
3. Сохраните JSON-вывод команды в отчёт. Команда измеряет время `fs.readFile` и потокового чтения одного файла, число чанков и RSS-память до/после этапов.
4. Повторите эксперимент два-три раза на одном компьютере с тем же файлом. Укажите средние/характерные значения и среду: версия Node.js, ОС и размер файла.

| Метрика | `fs.readFile` | Readable Stream |
|---|---:|---:|
| Время, мс | Заполнить по выводу benchmark | Заполнить по выводу benchmark |
| RSS до чтения, МБ | Заполнить по выводу benchmark | Заполнить по выводу benchmark |
| RSS после чтения, МБ | Заполнить по выводу benchmark | Заполнить по выводу benchmark |
| Наблюдение | Весь файл возвращается одним буфером | Обработка идёт чанками |

RSS — снимок памяти всего процесса, а не гарантированный пик потребления только конкретной операции. На цифры влияют ОС, файловый кэш, сборка мусора, размер файла и предыдущие действия. Не следует заранее придумывать результаты: внесите реальные значения, полученные на машине, где выполнялась лабораторная.

**Почему Stream не загружает весь файл сразу?** Потому что источник выдаёт последовательные чанки, а обработчик может обработать очередную порцию и отпустить её до поступления следующих данных. Это обычно снижает пиковую память на больших файлах.

**Как связаны Readable, Transform и Writable?** Readable выдаёт данные, Transform преобразует их по мере поступления, Writable принимает результат. В проекте цепочка выглядит так: `createReadStream → Transform → createWriteStream`.

## Worker Threads

Тяжёлое вычисление — детерминированный цикл, который обновляет числовой хеш для большого количества итераций. Реализованы два режима:

```bash
node app.js compute main 12000000
node app.js compute worker 12000000
```

Оба режима считают одинаковый результат. В ходе работы запускается периодический таймер с сообщениями `Главный поток отвечает: tick ...`.

- В режиме `main` цикл выполняется в основном потоке JavaScript и блокирует его до окончания расчёта. Поэтому таймерные сообщения во время цикла не выводятся; после вычисления выводится результат.
- В режиме `worker` расчёт выполняется в `src/workers/compute-worker.js`. Основной поток остаётся свободен для Event Loop, поэтому может выводить периодические сообщения, пока Worker вычисляет результат.

Worker Thread подходит для CPU-bound задач — долгих вычислений. Асинхронное чтение файла освобождает основной поток на время ожидания I/O, но само по себе не переносит тяжёлый синхронный JavaScript-цикл в отдельный поток. Поэтому Worker и асинхронная операция с файлом решают разные задачи.

### Дополнение: child_process.spawn

`child_process.spawn` запускает отдельный процесс операционной системы. У него отдельное адресное пространство и собственный жизненный цикл; общение обычно идёт через stdin/stdout/stderr, IPC или файлы. Worker Thread — поток внутри одного процесса Node.js, который может обмениваться сообщениями и при необходимости использовать SharedArrayBuffer. Для CPU-bound JavaScript в этой работе используется именно Worker Thread, как требует методичка; `spawn` описан как дополнительная теория и не подменяет его.

## Вопросы к защите — краткие ответы

1. **Что хранится в `process.argv` и почему значения — строки?** Аргументы командной строки, переданные процессу; интерфейс ОС передаёт их как текст, поэтому числа нужно преобразовывать и валидировать.
2. **Чем argv отличается от stdin?** argv передаёт параметры при запуске; stdin — поток данных, которые программа может читать во время работы.
3. **Что делать при нехватке аргументов?** Проверить их количество, вывести правильный формат команды и завершиться с понятной ошибкой.
4. **Почему Stream не читает весь файл в память?** Он передаёт данные чанками и позволяет обрабатывать их последовательно.
5. **Что такое chunk?** Одна порция данных, поступившая от потока.
6. **Как связаны Readable, Transform и Writable?** Источник выдаёт данные, преобразователь меняет их, приёмник сохраняет или использует результат.
7. **Что делает pipe/pipeline?** Соединяет потоки в цепочку и передаёт данные; pipeline также помогает корректно обрабатывать ошибки и завершение цепочки.
8. **Зачем нужен Worker Thread?** Для вычислительной работы, которую иначе выполнял бы и блокировал основной поток.
9. **Чем Worker отличается от асинхронного чтения файла?** Асинхронный I/O не блокирует поток на ожидании операции ввода-вывода; Worker выносит исполняемый JavaScript-код в другой поток.
10. **Чем spawn отличается от Worker?** spawn запускает отдельный процесс ОС, Worker — отдельный поток внутри процесса Node.js.
